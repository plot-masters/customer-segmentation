Phase 1

Segmenting Blinkit customers based on their spending behaviour and delivery experience to identify distinct customer clusters (high, medium, and low spending) for targeted marketing strategies and increasing sales

Proposal

  1. Project Statement
    Across customer-centric businesses, one of the major goals for the organization is being able to predict the needs of its customers and how to best cater to their needs while maintaining high profitability. However, to make the solution feasible, the way forward would be to create groups of consumers that share similar spending patterns, allowing the businesses to create targeted marketing campaigns, improve customer satisfaction, demand-oriented product development, and therefore improve profitability.

  2. Business Goal
    The objective of this project is to develop a machine learning model that can create suitable and usable clusters/segments given the profile and purchases of the customer. The model should then be able to predict, within bounds of acceptable error, which segment a customer is likely to belong to. The model should allow stakeholders to make informed and data-backed decisions on product demand, campaign successes and customer retention.

  3. Data Source
    We will use the “Blinkit Sales Dataset” for this project. This dataset provides detailed information on product sales, visibility, item types, and outlet performance, making it ideal for performing sales data analysis and gaining insights into business trends. The dataset is well-structured and suitable for data preprocessing, exploratory data analysis, and predictive modeling tasks.

    • Source Platform: Kaggle
    • Dataset: Blinkit Sales Data (Vaghasiya 2025)

  4. Tools and Technology
    Following languages and libraries are planned to be used for this project. More libraries may be used and every non trivial library shall be updated.

    • Python
      • Core Libraries
        • Data Manipulation: Pandas, NumPy
        • ML: scikit-learn
        • Data Visualization & Storytelling: Matplotlib, Seaborn
      • Development Environment: VS Code, Google Colab, GitHub
    • Dashboard: Power BI

  5. Project Workflow
    The project is to follow a standard data science development lifecycle,

    1. Data Acquisition: Fetch the dataset from Kaggle using its API.
    2. Preprocessing: Handle missing values (if any), encode categorical variables, and
      check for data inconsistencies.
    3. EDA: Analyze features to understand their relationship with attrition using statistical summaries and visualizations.
    4. Feature Engineering: Create new features from existing ones if necessary to improve model performance.
    5. Modeling: Train several clustering models (e.g., K Means Clustering, PCA, Decision Trees).
    6. Evaluation: Assess model performance using metrics like Accuracy, Precision, Recall, and F1-Score. Select the best-performing model.
    7. Visualization: Create an interactive dashboard in Power BI to present the key findings and predictions to stakeholders.

  6. Data Extraction
    The “Blinkit Sales Dataset” is acquired directly from the Kaggle repository. To ensure a professional and reproducible workflow, manually downloading the files is not done.
    Instead, we will perform the following steps:

    • Automate the Process: We will write a Python script that utilizes the official Kaggle API to connect to the source and download the dataset.
    • Ensure Reproducibility: This scripted approach guarantees that the data extraction process is consistent and can be easily re-run by any team member or reviewer.
    • Prepare for Analysis: The script will handle the unzipping of the downloaded files and load the data directly into a Pandas DataFrame, making it immediately available for the next phase of our project.
    • Notebook: Analysis Notebook

Data Cleaning

Dropping Irrelevant Columns

The drop_irrelevant_columns function removes columns that have no analytical value. This ensures the dataset remains focused on variables that contribute to downstream modeling or insights.

Removing High-Missing-Value Columns

The drop_high_missing_value_columns function eliminates columns where the proportion of missing values exceeds a specified threshold. This prevents sparsely populated fields from skewing analysis or requiring excessive imputation.

Imputing Missing Values

The impute_missing_values function fills missing entries based on column data types. Numerical fields use median imputation, categorical fields use mode, and all other types default to forward-fill. This maintains data consistency while preserving distribution characteristics.

Removing Duplicates

The remove_duplicates function removes duplicate rows and reports how many were dropped. This ensures data integrity and prevents inflated counts or biased analysis.

Handling Outliers

The handle_outliers function caps outlier values using the Interquartile Range method. Values below the lower bound or above the upper bound are replaced with the respective caps, reducing the influence of extreme values without complete removal.

Converting to Datetime

The convert_to_datetime function converts specified columns into datetime format. Invalid formats are coerced into missing values. This enables time-based operations and calculations.

Calculating Delivery Delay

The calculate_delivery_delay function computes the delay between promised and actual delivery times in minutes. It expects both fields to be datetime objects and adds a new column representing the delay duration.

Converting Categorical-Like Columns

The convert_categorical_like_columns function casts selected columns into the pandas category data type. This optimizes memory usage and clarifies the column’s semantic meaning.

Saving the Cleaned Dataset

The save_cleaned_dataset function writes the cleaned DataFrame to disk as a CSV file, prints final dataset characteristics, and returns the cleaned DataFrame for further use.

Feature Engineering

Aggregating Customer Data

The aggregate_customer_data function generates a customer-level dataset by aggregating order and delivery information. It computes mean order value, total spend, order count, average delivery delay, and identifies the most frequently used payment method and most common delivery status. This transforms transactional data into customer-centric metrics suitable for modelling.

One-Hot Encoding Categorical Features

The one_hot_encode_categorical_features function converts categorical attributes (most_used_payment and most_delivery_status) into one-hot encoded variables. This prepares these fields for machine learning models that require numerical inputs while preserving categorical distinctions.

Handling Numerical Features

The handle_numerical_features function applies appropriate transformations to numeric customer-level fields:

  • Standardization of avg_order_total
  • Log transformation and standardization of total_spent to reduce skew
  • Robust scaling of avg_delay to limit the influence of outliers
  • Min-max scaling of num_orders to normalize range

These transformations enhance model performance by improving feature distribution and comparability.

End-to-End Customer Data Processing

The process_customer_data function orchestrates the complete feature engineering pipeline. It aggregates customer metrics, encodes categorical fields, applies numerical transformations, and generates diagnostic visualisations including a correlation matrix and histograms for major engineered features. It returns both the processed dataset and the untransformed customer-level dataset.

Correlation Matrix Plot

The plot_correlation_matrix function visualises the correlation structure across engineered features. The heatmap highlights relationships, multicollinearity, and potential feature redundancy.

Feature-Level Histograms

The plot_histogram function produces histograms for individual transformed features. This aids in evaluating distributional characteristics after scaling and transformation.

Robust Scaling for Average Delay

The code applies a RobustScaler to the avg_delay feature. Robust scaling subtracts the median and scales by the interquartile range, which reduces the influence of extreme outliers. This is appropriate for delivery delay data, which often contains long-tail values.

Descriptive Summary of Order Counts

The line customer_df['num_orders'].describe() outputs summary statistics for the num_orders column. This provides insight into distribution, central tendency, and spread before further transformations are applied.

Min-Max Scaling for Order Counts

A MinMaxScaler with a feature range of (−1, 1) is applied to num_orders. This transformation rescales the values into a consistent numerical range, improving model convergence and comparability across features.

Converting Boolean Columns to Integer Format

The final line converts all boolean columns into integer values (True => 1, False => 0). This ensures full compatibility with machine learning algorithms that do not accept boolean dtype and provides a uniform numerical representation for modelling.

Dropping Identifier Columns

The code removes the customer_id column from the dataset prior to model preparation. Identifier fields carry no predictive value and can distort scaling or model fitting, so they are excluded from feature matrices.

Standardizing All Features

A StandardScaler is applied to the full feature set. This transformation centers each feature to mean zero and scales to unit variance, ensuring:

  • All features contribute proportionally
  • Gradient-based models converge more reliably
  • Distance-based models (k-NN, clustering) behave consistently

The result is stored in X_scaled, which becomes the fully standardized numerical feature matrix.

Saving the Processed Dataset

The final processed customer DataFrame is saved to disk as customer_df_processed.csv. This preserves the engineered feature set for downstream modelling, validation, and reproducibility.

Cluster Modelling

Executing K-Means Clustering

The perform_kmeans_clustering function runs the K-Means algorithm across multiple values of k and evaluates clustering quality. It applies PCA to reduce dimensionality for visualisation and uses three standard clustering metrics to assess performance:

  • Silhouette Score – Measures cohesion and separation of clusters.
  • Davies–Bouldin Index – Lower values indicate better-defined clusters.
  • Calinski–Harabasz Score – Higher values indicate better separation.

For each k, the function:

  1. Fits the K-Means model on PCA-reduced data.
  2. Visualises clusters in two principal components.
  3. Records performance metrics.
  4. Consolidates PCA coordinates and cluster labels for export or further analysis.

The function returns a dictionary of clustering scores and a combined DataFrame containing PCA-transformed coordinates, cluster assignments, and their corresponding k values.

Exporting Model Data

The export_model_data function saves the full cluster assignment dataset, including PCA dimensions and cluster labels, to a CSV file. This preserves the clustering output for reporting, validation, and downstream modelling workflows.

Basic Inference

Silhouette Score vs Number of Clusters

The silhouette score decreases sharply as k increases, with the highest score at k = 2. This indicates that the two-cluster solution yields the most cohesive and well-separated clusters, while additional clusters lead to overlap and poorer structure.

Davies–Bouldin Score vs Number of Clusters

The Davies–Bouldin index increases steadily with higher k, meaning cluster separation becomes worse as more clusters are introduced. The lowest score at k = 2 again suggests this is the most distinct and compact clustering.

Calinski–Harabasz Score vs Number of Clusters

The Calinski–Harabasz score decreases consistently as k increases, showing reduced between-cluster separation relative to within-cluster dispersion. The highest score at k = 2 confirms that the two-cluster model achieves the strongest overall partition.

Overall Conclusion: All three metrics consistently indicate that k = 2 provides the best clustering configuration for this dataset.

Basic Inference

Silhouette Score vs Number of Clusters

The silhouette score decreases sharply as k increases, with the highest score at k = 2. This indicates that the two-cluster solution yields the most cohesive and well-separated clusters, while additional clusters lead to overlap and poorer structure.

Davies–Bouldin Score vs Number of Clusters

The Davies–Bouldin index increases steadily with higher k, meaning cluster separation becomes worse as more clusters are introduced. The lowest score at k = 2 again suggests this is the most distinct and compact clustering.

Calinski–Harabasz Score vs Number of Clusters

The Calinski–Harabasz score decreases consistently as k increases, showing reduced between-cluster separation relative to within-cluster dispersion. The highest score at k = 2 confirms that the two-cluster model achieves the strongest overall partition.

Overall Conclusion: All three metrics consistently indicate that k = 2 provides the best clustering configuration for this dataset.

Cluster Overview

The K=2 clustering solution separates customers into one large group and one smaller group. Cluster 0 contains the majority of customers, while Cluster 1 represents a smaller segment with distinct behavioural patterns.

Cluster Characteristics

Cluster 0 Customers in this cluster place slightly more orders, spend more overall, and experience very low delivery delays. Their orders are almost always delivered on time, and the most common payment method is Card.

Cluster 1 Customers in this group make fewer purchases, spend less overall, and face significantly higher delivery delays. Most of their orders are classified as slightly delayed, and they also commonly use Card as the preferred payment method.

Behavioural Distribution

Payment method usage is similar across clusters, though Cluster 0 shows a slightly higher proportion of Card payments. Delivery performance is the strongest separator: Cluster 0 is entirely on time, whereas Cluster 1 is dominated by delayed deliveries.

Segment Interpretation

The clusters can be interpreted as:

  • On-Time High-Value Customers (Cluster 0): Higher spending, more frequent orders, consistently timely deliveries.
  • Delay-Affected Low-Value Customers (Cluster 1): Lower spending, fewer orders, and substantially higher delivery delays.

This segmentation highlights operational differences in delivery performance and their association with customer value.
